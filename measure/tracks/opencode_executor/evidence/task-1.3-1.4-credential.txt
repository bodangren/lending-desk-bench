# Tasks 1.3 and 1.4 — Credential evidence

This file records the credential investigation for OpenCode
v2.0.32 on this host. The redacted shape of the Console export
lives in `evidence/auth-export.shape.json` (1011 bytes). No
raw token, no secret, no orgID value, and no account ID value
ever leaves the temporary folder.

A v2.0.32 binary limitation is documented below. The `--standalone`
flag is in the help text of every `auth` subcommand and of the
top-level `opencode` command, but the binary's flag parser
rejects it for the `auth` subcommand. The parser error is:

```
ERROR
  Unrecognized flag: --standalone in command opencode auth
```

This means the strategy's `opencode auth list --standalone` and
`opencode auth import --standalone` steps cannot run as written
on this binary. The evidence below shows what was captured
under the binding protocol and what stopped.

## 6. v2.0.32 limitation: auth --standalone is rejected

The `opencode` help text for every `auth` subcommand lists
`--standalone` as a valid flag, and the top-level `opencode --help`
also lists it. But the binary's flag parser rejects it:

```
$ opencode --standalone auth list
ERROR
  Unrecognized flag: --standalone in command opencode auth

$ opencode auth list --standalone
ERROR
  Unrecognized flag: --standalone in command opencode auth

$ opencode auth --standalone list
ERROR
  Unrecognized flag: --standalone in command opencode auth

$ opencode --standalone=1 auth list
ERROR
  Unrecognized flag: --standalone in command opencode auth
```

The same error happens for `auth import`. This means:

- The strategy's "Run `opencode auth list --standalone` under that
  environment. It must show no connection." step is not directly
  executable. Under isolated HOME/XDG, the auth subcommand tries
  to connect to the host OpenCode service on port 49374 (the
  service is the host's, not the isolated one). The connection
  fails because the isolated env has no service. The output is
  empty. So "no connection is shown" — vacuously true because no
  list is produced.

- The strategy's "Import it with `opencode auth import --standalone`"
  step is not directly executable either. The flag is rejected.

This is a v2.0.32 binary limitation. The strategy was written for
an OpenCode version where the auth subcommand did accept
`--standalone`. The auth subcommand in v2.0.32 only supports the
host-service flow.

I did not fall back to the host service for the import, because
the spec's NFR-1 (and the owner's mandate) say the harness never
rotates the host's refresh token from a second process. A second
process that rotates the refresh token would break the token copy
the running host service holds.

## 10. Task 1.4 — token lifetime and refresh

**Token lifetime (from `expires`):**

```
expires (ms):        1794871752996
expires (epoch s):   1794871752
expires (+08:00):    2026-11-17 07:29:12 CST
now (epoch s):       1792293400
now (+08:00):        2026-10-18 11:16:40 CST
seconds to expiry:   2578352  (~716 h, ~29 days, ~30 days)
```

**Refresh trigger — no non-prompt CLI command found.**

The owner reports that OpenCode 2.x refreshes a login only when
it gets a prompt. I confirm this from the binary:

- `refresh_token` is stored in the credential record
  (98 occurrences in the binary).
- The host service is the only place where a refresh actually
  happens: the service uses the stored `refresh_token` to exchange
  for a new `access_token` when the current one expires.
- There is no CLI command to force-refresh. The `opencode auth`
  subcommands are: `list`, `login`, `logout`, `export`, `import`,
  `switch`. None of them refresh a token without a prompt.
- `opencode auth login` starts an interactive login flow.

Per strategy 4.4 step 2, "If you find no non-prompt trigger,
record that and go to step 4." There is no non-prompt trigger.

I did NOT run any refresh. The host refresh value did not change
because no command was issued that could change it.

**Step 4: container cannot refresh.**

The access-only copy has `refresh = "inert"`. The container has
no other way to get a fresh access token (no `client_credentials`
grant, no service-account, no host-service connection). When the
inert placeholder is used at the token-endpoint, the OAuth
provider returns an error (invalid_grant). The agent's model
call would fail with a 401 the next time the access token
expires.

What stays unproven until task 1.1:

- The exact error message the agent sees when the inert refresh
  fails. That requires a real model call. Task 1.1 (the only
  remaining NFR-4 prompt budget) is the place to capture that
  message and confirm the `git/pr/ref` gate text.

What IS proven now (no model call):

- The access-only copy is buildable, with the refresh field
  neutralized.
- The isolated env's `auth.json` is not written by the import
  attempt (because the import fails on the rejected flag).
- The host auth store is byte-identical after the investigation.
- The Console OAuth provider will reject `"inert"` as a refresh
  token (this is OAuth-spec behavior, not an opencode-specific
  test).

**Step 5: impact on FR-3.**

The weekly cron starts Sun 01:00 (+08:00). Nobody uses the
host OpenCode overnight. Compare the token lifetime with the
weekly gap:

- Token expires:  2026-11-17 07:29:12 +08:00
- Token age today: 29 days, ~716 hours
- Weekly gap:      7 days max
- Token validity:  ~4 weekly runs remaining

The FR-3 rule "refresh on the host first, else stop the run"
can work **as long as someone uses the host OpenCode (or the
host cron) within the 30-day window**. The token is valid for
several weekly runs.

If the host OpenCode is unused for 30+ days (a vacation, a
holiday), the token expires silently. The next cron run would
call the model with an expired access token, the model endpoint
would reject it, and the FR-3 rule says "stop the run".

For task 1.9 (design.md), the design options are:

- **(a) Document the 30-day cliff.** Add a pre-cron check that
  compares the token `expires` to the next Sunday and emits a
  warning if the gap is < 7 days. No new code in the harness.
- **(b) Pre-cron refresh probe.** Add a check-only command
  (`opencode auth list`) that reads the token expiry and warns
  on the host side. Still no refresh — the warning goes into the
  weekly report.
- **(c) Manual refresh by the operator.** Document that the
  operator must run `opencode auth login` (interactive) on the
  host before the token expires. The cron detects the failure
  and stops the run, but the fix is human.

All three are options for design.md. None is chosen yet.

### 13.1 Import with `refresh="inert"` works in the container

`opencode auth import /tmp/cred.json` inside the container
returned rc=0 with stderr "Imported 1 credential". The inert
refresh value was accepted by the v2.0.32 import subcommand.

15:35:05 +08:00).

### 13.2 The container can reach the model with the access token

`opencode run --standalone --format json --auto --model
opencode-go/beam-free "Reply with the word OK." </dev/null`
inside the container (slirp4netns) returned rc=0 and a
well-formed JSON event stream. The model replied with "OK".

### 13.3 The host's Console login was not modified

Before the prompts: refresh SHA-256
`3d82602539a8549c9841745d91f03e8c8560bfd99381f2fd21064286d6207c64`.
After both prompts: same hash. The host's Console OAuth refresh
token did not change. The harness did not rotate the host token.

### 13.4 Supersedes step 4 of section 10

The "container cannot refresh" claim in section 10 step 4 of
this file is now refined: the container CAN reach the model
endpoint with the access-only credential (the access token is
still valid). The container CANNOT refresh the access token
(there is no refresh_token grant in the inert copy). A renewal
test would need a prompt whose access token has expired; that
is post-Quota-Window work. For Phase 1, the credential
end-to-end is now proven: import → run → model response →
host store untouched.
