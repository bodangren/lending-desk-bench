# Task 1.8 — Token usage format

All evidence in this file comes from the live prompts in task 1.1
and from the offline probes of the evidence-fix turn (2026-10-18).
The container setup is identical (rootless Podman, pinned image,
read-only binary, private tmpfs, generated config). The redacted
event streams are in `evidence/live1-event-stream.redacted.json`
and `evidence/live2-event-stream.redacted.json`.

Sections 1, 2, and 4 were corrected in the evidence-fix turn:
the O3 conclusion (section 3), the parser statement (section 4),
and the final-step usage finding (section 1). Sections 5 to 8 are
new evidence from the offline usage-source probe.

## 1. Event types observed

### 1.1 Live prompt 1 ("Reply with the word OK.", model opencode-go/beam-free)

- `step_start` (beginning of agent step)
- `text` (model output: "OK")

### 1.2 Live prompt 2 (O3 probe: "Use the task tool once to run a
subagent that replies OK. Then reply DONE.", model opencode-go/beam-free)

- `step_start` (agent step begins)
- `tool_use` (subagent tool call, state.status="completed",
  state.input={"agent":"general", "description":"Reply OK",
  "prompt":"Reply OK."})
- `step_finish` (step complete, reason="tool-calls")
- `step_start` (second agent step begins)
- `text` (model output: "DONE")

All events are well-formed JSON with `type`, `timestamp`,
`sessionID`, and `part` fields.

### 1.3 Finding: the final step can lack usage (evidence-fix turn)

Neither live stream has a `step_finish` event for its last step.
Stream 1 has no `step_finish` at all. Stream 2 ends with the
`text` event "DONE" and no `step_finish` for that second step.
So the `--format json` event stream can lack token usage for the
final step of a run. The event stream alone is not a complete
usage source for FR-7. Section 6 gives the complete source.

## 2. Token usage fields (from `step_finish.tokens`, O3 probe)

The `step_finish` event in the O3 probe contains a `tokens` object
with these fields:

```json
{
  "input": 80,
  "output": 31,
  "reasoning": 32,
  "cache": {
    "read": 4096,
    "write": 0
  }
}
```

Additional fields on `step_finish.part`:
- `reason`: "tool-calls"
- `cost`: 0

Field summary:

| Field | Type | Per-step or cumulative? |
|---|---|---|
| `input` | number (tokens) | per-step |
| `output` | number (tokens) | per-step |
| `reasoning` | number (tokens) | per-step |
| `cache.read` | number (tokens) | per-step |
| `cache.write` | number (tokens) | per-step |
| `cost` | number (USD) | per-step |

The fields are per-step, not cumulative. The recost formula in
`go-cost.ts` uses input, output, cacheRead, and cacheWrite:

```
JSON event field  →  go-cost.ts Usage field
─────────────────────────────────────────
input             →  input
output            →  output
reasoning         →  counted as output (spec FR-7)
cache.read        →  cacheRead
cache.write       →  cacheWrite
```

The `reasoning` field is reported per-step. The recost counts it
as output. The `cost` field in the JSON stream is advisory (the
economics use the go-pricing.json recost, not the provider-reported
cost; spec FR-7).

## 3. Subagent token usage in the parent event stream (O3 branch)

The O3 probe used the `subagent` tool. The tool_use event shows
that the subagent ran its own session
(`evidence/live2-event-stream.redacted.json`, `state.output`:
`<subagent sessionID="ses_…" state="completed">`).

The subagent's token usage is **not** in the parent event stream:

- The only usage record in the parent stream is the first step's
  `step_finish.tokens` with `input: 80` and `cache.read: 4096`.
  The 80-token input size alone is not the proof (a prompt could
  in theory fit into the 4096 cache-read budget); the proof is
  the two facts below.
- No event in the parent stream carries the subagent session's
  own token totals.
- The second step (the "DONE" reply) has no `step_finish` at all
  (section 1.3).

The earlier claim that the subagent tokens are "aggregated" into
the parent step (`input: 80`, `cache.read: 4096`) was not
supported by the evidence. The evidence-fix turn removed it.

The owner rule: allow `subagent` only if its token usage is in
the parent event stream. It is not.

O3 branch: **deny `subagent`**.

## 4. What the harness must parse (corrected in the evidence-fix turn)

`harness/usage.ts` parses the **Pi transcript** (a Pi JSONL session
log with `message_end` and `turn_end` events; `harness/usage.ts`
lines 1–54). It does not parse an OpenCode stream or store.

FR-7 needs a **new OpenCode parser**. The `--format json` event
stream is a different format, and per section 1.3 it can lack the
final step's usage. Section 6 names the complete source that the
new parser reads. Phase 2 (task 2.5) writes the parser tests
against the fixture.

## 5. Offline probe: where OpenCode keeps token usage

Probe of the evidence-fix turn, offline, no network, no live
prompt. Setup identical to task 1.1 and task 1.7: rootless
Podman, `--network=none`, pinned image
`docker.io/library/node@sha256:6c74791e…`, the opencode binary
bind-mounted read-only at `/usr/local/bin/opencode`, ripgrep
bind-mounted read-only at `/usr/local/bin/rg`, private HOME and
XDG dirs on the tmpfs, `OPENCODE_CONFIG` pointing at the
generated config.

One offline `opencode run --standalone --format json --auto
--model opencode-go/beam-free "Reply with the word OK."` created
one session and exited 1 with `provider.no-route` (expected
offline; ledger row 6, live=no). The store under `XDG_DATA_HOME`
holds `opencode.db`, an SQLite database.

### 5.1 Database schema (`XDG_DATA_HOME/opencode/opencode.db`)

The `session_v2` table has one row per session with these token
columns: `tokens_input`, `tokens_output`, `tokens_reasoning`,
`tokens_cache_read`, `tokens_cache_write`, and `cost`. The
offline session row holds zeros (no model call happened).

A structure check of the host store (keys only, no message text
read) shows an assistant row of `session_message` carries the
keys `time`, `agent`, `model`, `content`, `snapshot` — no tokens
field. The per-message rows do not hold the usage. The session
row holds the totals.

### 5.2 `opencode session list` (offline, rc=0)

Lists the sessions of the isolated store, newest first.

### 5.3 `opencode session export <sessionID>` (offline, rc=0)

Prints JSON with the top keys `info` and `messages`. The `info`
object holds the whole-session usage:

- `info.tokens`: `{input, output, reasoning, cache: {read, write}}`
- `info.cost`
- `info.model.variant` (the offline run records `"default"`, which
  also confirms the O1 default-variant behavior)
- `info.outcome`

The full redacted output is in
`evidence/offline-session-export.redacted.json`.

### 5.4 `opencode stats` (offline, rc=0)

Prints a summary only ("1 session … 1 prompt · 0 steps · 0
tokens"). It is an aggregate view. It is not a per-run usage
source.

## 6. FR-7 usage source (proposal for design.md)

The entry script runs `opencode session export <sessionID>` inside
the container after `opencode run` returns, and writes the JSON to
the run artifacts. The sessionID comes from the event stream
(every event carries `sessionID`). The new parser reads
`info.tokens` (whole-session totals: input, output, reasoning,
cache.read, cache.write) and `info.cost`.

This source is complete: it does not depend on a final
`step_finish` event (section 1.3). The `--format json` stream
stays as a cross-check.

Open item for task 4.3: the offline probe proves the field shape
on a zero-token session. The first live smoke run (task 4.3)
confirms the non-zero totals. Phase 2 tests each candidate source
against the fixture (task 2.5).
